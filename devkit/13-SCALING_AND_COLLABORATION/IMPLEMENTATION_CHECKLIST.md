# Implementation Checklist — Scaling & Collaboration

**Status:** Planning
**Created:** 2026-09-27

This plan fixes three things found while reviewing the current architecture: every edit rewrites the entire page's JSON instead of just what changed, concurrent edits from two people can silently overwrite one another with no safety check, and there's no Projects layer above Pages yet. It's organized into six tracks below — Track B (normalizing widgets) is the critical path everything else improves on; Tracks D and E can run in parallel with it.

## Undo/Redo Bug Fixes (found during B3 verification, 2026-09-28)

Not part of the original plan -- discovered while verifying B3 with a real multi-step undo/redo sequence (add widget → move it → undo → undo → redo → redo). All three fixes below are in `backend/src-js/services/operationHistory.service.js`, `backend/src-js/services/undoRedo.service.js`, and `backend/src-js/websocket/page.handler.js`.

- [x] **Fix 1 — `popFromUndoStack` returned the wrong operation.** Its SQL did `RETURNING undo_stack[1]` in the same statement as `SET undo_stack = undo_stack[2:...]` -- `RETURNING` evaluates *after* `SET`, so it read the stack's new top (or `NULL` if the stack had just emptied), never the operation actually popped. This affected every call, regardless of stack size -- undo had likely never returned the correct operation. Fixed by reading `redo_stack[1]` instead: the same statement's `SET` already pushes the popped value there, so it holds the correct pre-pop value post-update.
- [x] **Fix 2 — inverse of an appended `add` was an invalid path.** `undoRedoService.generateInverse` built the inverse of `{op:'add', path:'/widgets/-'}` as `{op:'remove', path:'/widgets/-'}` -- but `-` only means "append" for `add`, it doesn't address an existing element, so the remove failed with `OPERATION_PATH_UNRESOLVABLE`. Added `resolveConcretePath(documentBeforeOp, path)`, which resolves `-` to the concrete index (the parent array's length before the add) before building the inverse.
- [x] **Fix 3 — redoing wiped the rest of the redo stack.** `pushToUndoStack`'s SQL unconditionally reset `redo_stack = ARRAY[]::UUID[]` -- correct for a normal edit (a new edit should invalidate forward history), but the `page:redo` handler also calls it to make the redo itself undoable, which clobbered whatever `popFromRedoStack` had just correctly left behind for further redos, collapsing multi-level redo to one step. Added a `preserveRedoStack` option (default `false`, unchanged for normal edits); the redo handler now passes `true`.
- [x] **Fix 4 — empty-operation crash.** A related crash surfaced once Fix 3 let a second redo actually reach further logic: when OT transforms an operation down to zero ops, `page:redo` had no guard for that (unlike `page:patch`, which already handles it), so it fell through to `saveOperation` with an empty array, crashing in `extractOperationType` (`operation[0].op` where `operation` was `[]`). Added the same early-return guard `page:patch` already has, plus a defensive `operation?.op` in `extractOperationType` itself.
- [x] **Fix 5 — a second consecutive redo was silently dropped.** ✅ (2026-09-28) Root cause: `getOperationsSinceVersion` (in `operationHistory.service.js`) filtered only by `page_id` and `from_version`, with **no `user_id` filter at all** -- so a user's own prior undo/redo steps (each recorded as its own `operation_history` row) counted as "concurrent operations" against their own *next* undo/redo. After a couple of undo/redo steps, OT was transforming against a growing pile of the user's own history instead of genuine edits from someone else, and eventually cancelled the operation down to zero ops.
  — This is specific to undo/redo, not a general OT problem: `patchService.getPatchesBetweenVersions` (used for the regular `page:patch` stale-client-rebase case) was checked and does **not** have this bug -- there, "any patch since the client's last known version, regardless of author" genuinely is what the client needs to rebase against, including its own earlier patch from a stale multi-tab session. The two functions solve different problems; only the undo/redo one needed fixing.
  — Fix: added an optional `excludeUserId` parameter to `getOperationsSinceVersion`, and pass `socket.userId` at both call sites (`page:undo` and `page:redo`) so a user's own operations are excluded from their own "what's concurrent" check. Conflict detection against genuinely different users is unaffected -- this only removes *self*-conflicts.

**Verified (2026-09-28):** full `test-undo-fix.js` sequence on a fresh page -- add → move → undo (reverts move) → undo (reverts add) → redo (re-adds) → **redo (re-moves)** all pass, including the second redo that was previously silently dropped. Also directly verified Track C's new `AND version = $expected` guard: the happy-path sequence above succeeded on every step (no false-positive conflicts), and a deliberately wrong expected version against a real page affected 0 rows (confirming the guard genuinely blocks a mismatch, not just that it stays out of the way). No backend errors logged across the run. Full page_widgets/page_data parity re-checked across all pages afterward (see note below on the parity script itself).

**Bonus, unplanned validation:** while this was happening, the *actual project owner* was independently using the live app (left running in a browser tab from earlier testing) and created three new real pages through the UI. All three came through correctly as metadata-only in `page_data` with their widgets properly in `page_widgets` -- meaning the B3 write path and the frontend Map refactor have already been exercised via genuine UI interaction, not just scripted tests.

**Housekeeping found along the way:** `database/verify-page-widgets-parity.js` predates B3 and was comparing `page_data.widgets` against `page_widgets` as if the blob were still authoritative -- every page touched since B3 shipped now correctly has *no* `widgets` key in its blob at all, which the old script reported as 9 false "extra row" failures. Not a data bug -- updated the script to recognize a metadata-only blob as the expected post-B3 state and skip the comparison for those pages instead of flagging it.

## Track C — Collaboration Correctness (no locking)

- [x] Confirm the per-row optimistic version check from B2 is in place — this is the actual fix, not locking ✅ (2026-09-28) — **confirming this surfaced a real, unfixed gap, not a rubber-stamp.**
  — What B2 actually shipped was version *bookkeeping* on `page_widgets` rows, not a guard against lost updates. The real gap was upstream: `UPDATE pages SET page_data = $1, version = $2 WHERE id = $3` in `page:patch`, `page:undo`, and `page:redo` had **no** `AND version = $expected` clause -- the exact missing compare-and-swap flagged all the way back at the start of this project's review. Two requests that both read the same `serverVersion` before either wrote back could both proceed; the second would silently overwrite the first with no error.
  — Fixed by adding `AND version = $expectedVersion` to all three `UPDATE pages` statements. A 0-row result now means a genuinely concurrent write landed between this request's read and write -- it's rejected (`page:conflict` / `page:undo:error` / `page:redo:error`, "please retry") instead of silently committing over someone else's change. For undo/redo, the operation is also correctly pushed back onto its stack on rejection (`popFromRedoStack`/`popFromUndoStack`), consistent with this handler's existing recovery pattern for other failure paths, so a rejected undo/redo doesn't leave the stacks pointing at an operation that never actually applied.
  — This is layered *underneath* the existing OT (which handles "the client's view was already stale when it sent the patch") -- this guard catches the narrower, faster race of two requests both starting from a view that was current *at read time*.
  — **Verified (2026-09-28):** backend boots clean with the guard in place; a full patch/undo/redo sequence against a real page succeeds normally on every step (no false-positive conflicts); a direct test with a deliberately wrong expected version against a real page affected 0 rows, confirming the guard actually rejects a genuine mismatch rather than just staying out of the way.
- [x] Optional: broadcast a lightweight, purely visual "this widget is being edited by X" indicator, reusing the existing selection-broadcast/presence pattern — awareness only, never an enforced block ✅ **already existed** (found 2026-09-28, built earlier in commit `fa19366`)
  — This was already fully implemented before this plan started: `page_canvas_view.dart` renders a solid orange border around a widget someone else has selected, plus a floating name-tag label above it (e.g. "Bob"), driven by `page:selection`/`page:selection:updated` and `PageState.otherUsersSelections`/`otherUsersNames`. Purely visual, never blocks the local user from also selecting/editing the same widget -- exactly the awareness-only behavior this item asked for. No new work needed; confirming it's real (not dead code) by reading the actual render tree, not just the event wiring.
- [x] Frontend: viewport virtualization — only build/render widgets whose bounding box intersects the visible canvas area, the real fix for rendering lag on large pages ✅ (2026-09-28, implemented; compiles clean; **not visually smoke-tested**)
  — `page_canvas_view.dart`: root widgets are now filtered through `_isRootWidgetNearViewport` before being built, using a `_visibleCanvasRect()` derived from the same transform + render-size lookup `_sendViewportUpdate` already uses for the follow feature (`context.findRenderObject()` + `_transformationController.value`), expanded by a 400px margin so widgets don't pop in/out abruptly during a small pan. Nested children are unaffected -- culling only applies at the root level, since a visible container still renders its full subtree internally.
  — Deliberately conservative: if layout info isn't available yet (e.g. the very first frame), it renders everything rather than risk hiding something. Under-culling costs a bit of extra render work; over-culling makes a widget invisibly vanish, which is the failure mode to avoid given this is a purely visual feature with no way to unit-test its correctness.
  — **Verified:** `flutter analyze` across the whole project comes back with zero errors after this change (checked once the shell tools recovered from a mid-session outage).
  — **Still not verified:** no visual smoke test. Static analysis confirms it's type-correct, not that the culling math is actually right on screen -- there's no automated way to check "did a widget incorrectly vanish while panning" from here. **Please pan/zoom around a page with several widgets spread out before trusting this.**

## Track D — Frontend Resilience ✅ Done (2026-09-28)

- [x] Wire up the already-written `PageCacheService` so opening a page reads from Hive first (instant) and reconciles with the server in the background, instead of today's plain network-only fetch ✅ (2026-09-28, D1)
  — `PageBloc._onLoadPage` now follows a cache-first pattern: if `PageCacheService.getCachedPage(pageId)` returns a hit, the BLoC emits it immediately (instant paint), joins the socket, and starts autosave — then fetches from the REST API in the background. If the server version is newer, a second emit updates the view; if the fetch fails and a cache hit was already painted, the error is silently swallowed (the user sees their last-known state rather than an error screen). If there is no cache hit at all, the original network-error path is preserved.
  — Also caches every successful server response via `PageCacheService.cachePage(page)`, so future cold-starts of the same page benefit from the cache.

- [x] Wire up offline patch queuing so a dropped socket connection queues patches instead of silently discarding them ✅ (2026-09-28, D2)
  — **Decision on `OfflineQueueService`:** the existing service targets REST widget endpoints (`POST /api/pages/:id/widgets`, `PUT .../:widgetId`, etc.) that don't exist in this API. It was intentionally *not* wired up. A new, purpose-built `OfflinePatchQueueService` was built instead (`frontend/lib/core/services/offline_patch_queue_service.dart`), which stores exactly what the real `page:patch` socket event needs: `{kind, pageId, patches, clientVersion}` in the existing Hive `_operationsBox`.
  — `PageWebSocketClient.sendPatch()` changed from `void` to `bool` — returns `false` when the socket is disconnected. `_sendPatchAndClearSync` in `PageBloc` routes accordingly: connected → existing timer path; disconnected → `OfflinePatchQueueService.enqueue()`, updates `pendingSyncCount` in state.
  — Replay fires on the `page:joined` event (not raw socket `onConnect`) — the server sets `socket.pagePermission` during the join handshake, so sending `page:patch` before that would be rejected. Replay is ack-based: each queued patch waits up to 8 seconds for `patchAppliedEvents`, `conflictEvents`, or `patchErrorEvents` before advancing; stops on first failure to preserve causal ordering of subsequent patches.
  — Two new fields added to `PageState`: `isOffline` (updated from `PageConnectionState` stream) and `pendingSyncCount` (patches queued locally, not yet acked), so the UI can distinguish "offline, queued" from a real save error.
  — **Known, accepted gap:** at-least-once delivery — if the connection drops in the narrow window after the server applies a patch but before its ack reaches the client, the patch will replay on the next reconnect. No dedup for that case; it's not an oversight.

- [x] Decide the fate of `DraftAutoSaveService` — wire it in ✅ (2026-09-28, D3)
  — Wired in alongside the offline queue rather than dropped: the two serve different failure modes. The offline queue handles "socket disconnected while editing" (patches queued, replayed on reconnect, deleted on ack). Drafts handle "app crashed / process killed" before any patches could be sent — a Hive snapshot of the page at its last known state, independently recoverable.
  — `PageBloc` lifecycle: `startAutoSave(pageId)` on every successful page load (both cache-hit and server-fetch paths); `markModified(pageId, page)` in `_sendPatchAndClearSync` on every mutation; `deleteDraft(pageId)` in `_onConfirmPatchApplied` after a server ack; `stopAutoSave()` in `_onClearPageState` and when switching pages in `_onLoadPage`; `dispose()` in BLoC `close()`.
  — **What's NOT verified, and needs a human:** no browser-automation tool is available in this environment. Cache-first loading (cache hit → instant paint), offline queue (disconnect mid-edit, reconnect and see queued patches replay), and draft recovery (simulate a crash) all require manual interaction. **Please smoke-test these three flows before trusting them in anything beyond local dev.**
  — `flutter analyze`: 417 issues, all pre-existing (`avoid_print`, `invalid_use_of_visible_for_testing_member` on `emit` in stream callbacks, pre-existing dead code). Zero new errors from Track D. `flutter test`: 20/21 pass; the one failure (`widget_test.dart: App starts with login screen`) is a pre-existing, unrelated issue confirmed unchanged by `git diff`.

- [ ] Add a `project_id` foreign key on `pages`
- [ ] Add a `project_permissions` table — project access grants all its pages by default, with `page_permissions` entries acting as page-level overrides
- [ ] Frontend: add a projects list screen above the current page dashboard; page creation and loading become project-scoped
- [ ] Decide and implement cascade behavior: deleting a project soft-deletes its pages, consistent with how pages already use `deleted_at`
- [ ] Later, optionally: introduce a `workspaces` table above projects for full multi-tenant plan/quota support and Postgres row-level security keyed on `workspace_id`

## Suggested Execution Order

**Now:** Track A — all quick, independent, immediately valuable, no schema change.

**Next, as the main sequential effort:** Track B1 → B2 → B3, in that order — each sub-phase depends on the previous one landing correctly. Track C hangs off Track B2 specifically.

**In parallel with Track B, whenever convenient:** Track D and Track E — neither touches the `widgets` table, so neither blocks nor is blocked by the migration.

**Last:** Track F, once Track A's Redis adapter and Track B's per-row optimistic writes are both in place — this is where the horizontal-scaling story actually gets proven, rather than accidentally working because only one instance has ever been run.
