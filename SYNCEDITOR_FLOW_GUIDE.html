01 · Overview

What this is

SyncEditor is a Figma-style canvas editor where multiple people edit the same page at once: drag widgets, see each other's cursors, follow one another's viewport, comment with @mentions, and undo/redo — all synced live over WebSockets.

Frontend: features/canvas/* is an older widget-based editor that main.dart never wires up — the live path is entirely features/page/*. Everything below describes the live path only.

03 · Request lifecycle

From opening the app to editing together

  1. 1

    Auth

    Login/register hits the REST API; the server checks bcrypt, issues a JWT ({userId, email}). The Flutter client stores it in Hive and attaches it to every REST call and, later, the socket handshake.

    POST /api/auth/loginPOST /api/auth/register
  2. 2

    Dashboard & open a page

    The dashboard lists pages the user has permission on, then fetches the chosen page's full page_data JSONB blob and version (cache-first via Hive, then network).

    GET /api/pagesGET /api/pages/:id
  3. 3

    Join the realtime room

    The socket connects with the JWT as handshake.auth.token and emits a join. The server verifies access against pages + page_permissions, joins the Socket.IO room, writes presence to Redis with a per-user color, and replies with the current data, version, and permission level.

    page:joinpage:joinedpage:user:joined
  4. 4

    Edit a widget (JSON-Patch + OT)

    The client mutates local state optimistically, diffs old vs. new page data into an RFC-6902 JSON Patch, and sends it with the version it was based on. If another edit landed first, the server rebases the incoming patch against the intervening ones (operational transformation) instead of rejecting it outright. It then persists the new page_data + incremented version, saves an inverse patch for undo, and broadcasts to everyone else.

    page:patchpage:patch:appliedpage:patch:receivedpage:conflict
  5. 5

    Undo / redo

    Popping a user's per-page undo stack, transforming the stored inverse operation against anything that happened concurrently, applying it, and pushing the forward operation onto the redo stack — so undo stays correct even while others are editing.

    page:undopage:undo:appliedpage:redopage:redo:applied
  6. 6

    Presence: cursors & selection

    Cursor position and widget selection are broadcast to everyone else in the room (never echoed back to the sender) and cached in Redis with a 30-second TTL so stale cursors vanish automatically.

    page:cursorpage:cursor:updatedpage:selectionpage:selection:updated
  7. 7

    Follow mode

    Following another user stores the relation in Redis (1-hour TTL) and puts the follower's editor into read-only mode. When the followed user pans or zooms, the server looks up their followers and pushes the new viewport only to those sockets.

    page:follow:startpage:follow:startedpage:viewport:updatepage:viewport:updatedpage:follow:stop
  8. 8

    Comments & mentions

    Comments persist to Postgres and broadcast to the room; an @mention additionally resolves to a user ID and pushes a direct notification straight to that user's socket(s), independent of the room broadcast.

    comment:createcomment:createdcomment:mentioncomment:resolve
  9. 9

    Leave / disconnect

    An explicit leave or a dropped socket removes the active_editors row and the Redis presence/cursor keys, then tells everyone else the user is gone.

    page:leavedisconnectpage:user:left

04 · Persistence

What lives where

PostgreSQL

Source of truth. pages (JSONB page_data + version), page_permissions, patch/operation history for undo-redo, active_editors, comments, users. Legacy canvases/widgets tables still exist but are unused by the live path.

Redis

Ephemeral only, nothing authoritative: active users per page, cursors (30s TTL), follow relations (1h TTL), viewports (30s TTL). Losing Redis loses presence, not data.

Hive (client)

Local cache for instant page loads and offline access, a queue of mutations made while offline, and periodic draft autosave snapshots.
